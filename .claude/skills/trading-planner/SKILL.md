# 트레이딩 시스템 플래너

이 시스템의 발전 사이클은 **구현 → 측정 → 유지/폐기**이고, 계획의 실패는 두
가지로 나타난다: ① 이미 폐기된 것을 다시 만든다 ② 측정 없이 값을 정한다.
이 스킬은 그 두 실패를 계획 단계에서 막는다.

## 계획 전 필수 입력 — 이 순서로 읽는다

1. **`docs/trading/measurement.md`** — 측정 원장. 제안하려는 것이 이미
   측정·폐기됐는지, "예정된 판정" 표에 이미 잡혀 있는지 먼저 확인한다.
   여기 없는 아이디어만 새 계획 대상이다.
2. **예정된 판정·예약 트리거** — measurement.md 의 판정 표 + 세션의
   list_triggers. 새 작업이 진행 중인 측정의 입력을 바꾸면(감시목록 크기,
   소스 구성 등) 그 측정이 흔들린다 — 판정 뒤로 미루거나 측정과 독립임을
   확인한다.
3. **`docs/trading/known-issues.md`** — 알려진 문제. 새 기능보다 새는 돈이
   먼저다.
4. 최근 실측(그날 세션 관찰·일지) — 계획은 어제의 숫자 위에서 선다.

## 우선순위 — 이 저장소가 반복해서 쓴 판단 기준

순서대로 자른다. 상위 기준에서 갈리면 하위는 보지 않는다.

1. **지금 돈이 새는가** — 실거래 손실·회계 오염·가드 오작동이 최우선.
   (선례: 유령 포지션 정정, 수동 청산 미발주 버그, 원장-계좌 괴리)
2. **비용 대비 정보량** — 싸고 즉시 답이 나오는 측정이 비싼 구현보다 먼저.
   (선례: 이벤트 스터디 재실행 52초가 관제센터 설계를 결정했다)
3. **뒤 작업의 전제인가** — 측정 도구 교정이 그 위의 모든 판단보다 먼저.
   (선례: 목적어 교정·잔차화 없이는 랭킹 논의 자체가 무효였다)
4. 위 셋에 해당 없으면 **관측부터** — 새 아이디어는 관측 수집기로 시작한다.

## 새 아이디어의 경로 배치

들어온 아이디어는 반드시 넷 중 하나로 배치한다. "일단 구현" 은 없다.

| 경로 | 조건 | 다음 단계 |
|---|---|---|
| **관측 수집기** (기본값) | 예측력 주장이 없거나 미검증 | 원장 쌓기 + 판정 사전 확정 + 4주 트리거 (new-source.md) |
| **측정 도구** | 기존 데이터로 답할 수 있는 질문 | research/ 모듈 + 판정 기준 못박기 (measurement-flow.md) |
| **실행 변경** | 두 관문(잔차 IC + 랭킹 하네스/실현 R) 통과 **또는** 사용자 명시 결정 | 되돌릴 수 있는 형태(config·게이트)로, 보수적 기본값 |
| **보류** | 표본 미달·전제 미충족·모순된 근거 | measurement.md 에 보류 사유와 해제 조건 기록 |

배치 판단에 쓰는 질문 4개 (measurement.md 판정 원칙의 계획판):
① 측정이 있는가 — 없으면 관측부터 ② 되돌릴 수 있는가 ③ 틀렸을 때
실거래에 닿는가 — 닿으면 보수적으로 ④ 판정 기준을 미리 못박을 수 있는가
— 못 박으면 측정이 아니라 인상비평이다.

## 제안서 형식 — 사용자에게 내는 계획의 구조

사용자 결정 사항(리스크·자동발주·매매 설정·소스 편입·측정 통과 후 승격)은
계획에 **결정 항목으로 분리**해서 낸다 — 계획 안에 섞어 두면 승인 없이
실행된다.

```
무엇을        한 문장
왜 지금       우선순위 기준 몇 번에 걸리는가 + 근거 실측
비용          구현 규모 · API 예산(분당 콜) · 배포 필요 여부
판정          사전 확정 — 시점·지표·분할·표본 제외 (관측/측정 경로면 필수)
되돌리기      config 키 · 런타임 오버라이드 · 기본값
사용자 결정   승인이 필요한 항목만 따로
```

## 다단계 개발 계획 — 큰 작업을 자를 때

실거래 중인 시스템이라 큰 덩어리 전환은 금지다. 발굴 엔진 재작성(shadow →
collect → full, 각 3거래일 관찰)이 이 저장소의 검증된 틀이다.

1. **모든 단계는 끝날 때마다 커밋·배포 가능 상태** — 반쯤 배선된 채로 다음
   단계로 넘어가지 않는다
2. **신규 경로는 기존 경로와 병행 가동 후 교체** — 기록만 하는 단계(shadow)를
   먼저 두고, 관찰 기간(보통 3거래일)과 **전환 판정 기준을 계획 시점에
   못박는다.** 어긋나면 기간을 더 도는 게 아니라 원인을 고치고 다시 센다
3. **단계마다 롤백 수단을 명시** — 런타임 오버라이드가 최선, config 롤백이
   차선, 코드 되돌리기는 최후
4. **관찰 단계에서 무엇을 보는지 목록으로** — "이상 없는지 본다"는 계획이
   아니다. 지표·로그·원장 쿼리를 항목으로 적는다 (개장 직후 검증 A~F 선례)
5. 전환일은 직전 판정이 끝난 뒤에 잡는다 — 미리 예약하면 그 예약이 판정을
   압박한다

## 일정 규약

- **배포 창**: 평일 15:30 마감 후 ~ 17:30 야간 배치 전. 장중·배치 중 금지
  (사용자가 명시적으로 지시하면 예외 — 그때도 재시작 공백을 고지한다)
- **판정 예약**: 관측·측정을 만들면 그 자리에서 4주(또는 사전 정의) 트리거를
  등록한다. 질문은 docstring 그대로, "표본 미달이면 연기 보고" 조항 포함
- **API 대량 작업**(백필 등): 키움 점검(주말 저녁~) 회피, 페이지네이션 확인
- **주말·연휴**: TTL 1일 신호(nightly·flow)는 월요일 아침 만료 상태가 정상 —
  이를 장애로 읽는 계획을 세우지 않는다
- 30분 넘는 서버 작업은 systemd-run 독립 유닛 (MCP 재시작에 죽는다)

## 계획에서 하지 않을 것

- **measurement.md 확인 없이 제안** — 폐기된 것의 재제안이 가장 흔한 낭비다
  (발굴 랭킹·min_score·소스 가중치·screen 팔·성과 기반 강등은 전부 측정으로
  죽었다. 부활 조건도 이미 원장에 적혀 있다)
- 하루 표본으로 성과 판정 (기준선과 판정일이 정해진 측정만 판정한다)
- 진행 중인 측정의 입력을 바꾸는 작업을 판정 전에 배치
- 사용자 결정 사항을 계획이 대신 정하는 것
- LLM 을 점수·승격·주문 판단에 넣는 계획 (금지 목록 — trading-conventions)

## 산출 후

계획이 승인되면 구현은 **trading-conventions 스킬로 넘어간다** — 그쪽 라우터
(new-rule / new-source / wiring / measurement-flow / ship)가 구현 절차를
정한다. 계획 단계에서 정한 판정 기준·되돌리기·예산은 그대로 구현의 docstring
·config 주석·커밋 메시지가 된다.
