# 운영 런북

실계좌가 걸려 있는 시스템의 배포·설정·점검·사고 대응 절차.

## 원칙

- **서버 조회는 읽기 전용 우선.** `run_command` 는 승인 게이트가 있다
- **주문·매매 관련 명령은 실행하지 않는다.** 대사(reconcile)는 조회·기록 경로다
- **리스크·자동발주 등 매매 설정은 사용자가 결정한다** — 자동화 작업이 임의로 바꾸지 않는다
- 서비스 재시작은 `systemctl` 직접 호출이 아니라 MCP 도구(`restart_service`)로
  (대화형 인증 오류를 피한다)

## 배포

```
PR 머지(main) → deploy_service("trading")   # /opt/hosub-trading pull + 재시작
             → restart_service("dash")      # UI·프록시(static/·src/) 변경 시
```

배포 전 확인:

1. **장중(평일 09:00~15:30) 배포 금지** — 재시작이 매매 판단·청산 감시를 끊는다.
   불가피하면 포지션 0 확인 후
2. **17:30 야간 배치 중 배포 금지** — 배치 상태 API 로 진행 여부 확인.
   중단 시 재개는 되지만(일봉 기존분 스킵) 콜 예산을 버린다
3. 전체 스위트 통과: `trading` pytest + 루트 `pytest tests tnm/tests` + `node --check`
4. 실거래에 닿는 신기능은 **`enabled: false` 로 배포 → 다음 거래일 장중에 켜고
   30분 관찰** (배포와 활성화 분리 — 매매 데스크가 이 절차로 들어갔다)

배포 후 스모크(읽기 전용): 서비스 로그에서 기동 확인(감시목록 로드·엔진 루프
시작·WS 구독), `/api/scout`·`/api/status` 200, `ss -ltn` Recv-Q 0(이벤트 루프
정지 감시).

## 런타임 오버라이드 (`/data/trading/*.json`) — 배포 없이 바꾸는 것들

| 파일 | 내용 | 바꾸는 방법 |
|---|---|---|
| `engine.json` | 발굴 엔진 mode(shadow/collect/full)·freeze | API. **shadow=감시목록 동결**임에 주의 |
| `risk.json` | long_only·거래당 리스크·일일 목표/한도 | UI/API. **long_only 는 true 유지** — false 로 바꾸면 현물 불가 숏이 나간다(실사고) |
| `rules.json` | 기법 on/off | UI 토글. config 와 다르면 UI 쪽이 최신 사용자 결정 |
| `desk.json` | 매매 데스크 on/off·트레일링 | `POST /api/desk` |
| `night_bias.json` | 야간 리포트의 익일 국면 편향 | Cowork 야간 작업이 기록 |

config.yaml 기본값과 런타임 파일이 **다를 수 있다** — 운영 상태를 물을 때는
런타임 파일·API 를 본다. config 를 고칠 때는 코드 DEFAULTS 와의 동기도 확인.

## 개장 점검 목록 (평일 09:20경)

1. WS 연결 — 주말·새벽 키움 점검 시간에는 토큰 엔드포인트가 302를 돌려준다.
   **개장 전 복구가 정상**, 장중에도 302면 이상
2. 발굴 엔진 — 소스 6종 `fails=0`, 대량 축소(MAX_SHRINK) 경고 없음, 승격이
   게이트(특히 probation — 주말 유입은 당일 승격 불가)를 지키는지
3. 신호 엔진 — 사이클이 `scan_interval_sec` 근처인지(매매 tier 수에 비례해 늘어남)
4. 데스크 — 폴백 REST 콜 수(WS 살아 있으면 ≈0), 중복 발주 0건
5. 관측 수집기 — 첫 기록 적재 여부(신규 배포분 위주)
6. 전일 야간 배치 — picks 존재, 국면 산출

## 키움 API 주의사항 (실측)

- 레이트리밋은 **전 루프가 공유하는 단일 예산**이다 — 새 호출을 늘리면 다른
  루프가 굶는다. 감시목록 상한(max_trade 40)이 이 예산에서 유도된 값
- 주말·심야 점검 시간: OAuth 302 리다이렉트(html 페이지) — 재시도 백오프가 처리
- `ka10023` sdnin_rt 는 누적 거래량 %, `ka10015` strt_dt 는 뒤로 앵커,
  `ka10086` 은 qry_dt 필수, 음수 이중부호 `"--"` 값 존재
- 서비스마다 내부 토큰이 다르다(trading ↔ TNM: `TNM_TOKEN`)

## 사고 사례집 (전부 실사고 — 재발 방지 코드 존재)

| 사고 | 원인 | 재발 방지 |
|---|---|---|
| 유령 포지션 → 실현손익 오염 | 주문번호 수신만으로 open_position, 거래소 거부 미회수 | `reap_unfilled`(계좌 잔고 대조 void) |
| 수동 청산이 매도 미발주 | close 버튼이 원장만 닫음 | `execute_exit` 경유 + void 버튼 분리 |
| 숏 주문 발주 | `long_only: false` 로 변경돼 있었음 | true 복구 + 게이트 로그 |
| 마감 후 대량 강등(22종목) | '신호 없음'을 '후보 아님'으로 읽음 | `in_session` 마감 후 강등 금지 |
| 고아 감시항목 무한 강등 판정 | full 창이 남긴 잔재, 소스 무보고 | 단일 통로 + 회전·서킷브레이커 |
| 배치 중 배포로 1,200콜 유실 | 진행 상태 미영속 | 재개 로직 + job_marks |
| 보유 종목 감시목록 이탈 → 15분 묵은 가격으로 손절 판정 | 전량 교체가 보유 미확인 | 보유 보호 + 전량 교체 폐기 |
| 이벤트 루프 정지(연결 141 적체) | 무거운 작업을 스레드로 | offload 자식 프로세스, `ss` Recv-Q 감시 |
| news 어댑터 0건 무오류 | status 필터 오타('done'≠'ok') | `TNM_STATUS_OK` 상수 + 실값 검증 테스트 |
